UPSTREAM RUNTIME REPORT — two semantic regressions in the .oo runtime rewrite
================================================================================

Org:     idlescreen
Toolchain: openOODA-core (oodac + std + oodar)
Date:    2026-11-13
Upstream refs: openOODA-core/oodar  a53de08 (C runtime)  ->  master (2026-11-13,
             published as 9af908c, later hub asset 40ac871e... / upstream ab5ae7bc)

Two independent regressions came in with the C -> .oo runtime rewrite. Both are
silent: nothing errors, the runtime just answers a different question than it
used to. Defect A breaks UTF-8 rendering. Defect B breaks bit-exact
floating-point reproducibility against any libm-based reference.

Re-verified on 2026-11-13 against the newest published runtime (hub asset
40ac871e..., upstream ab5ae7bc): both defects are still present, and the
parity sweep still stands at 48/51 with the same three scenes.

FILED UPSTREAM on 2026-11-13:

  Defect A - codepoint -> byte primitives
      https://github.com/openOODA-core/oodar/issues/1
  Defect B - math is no longer libm-compatible
      https://github.com/openOODA-core/oodar/issues/2
  Defect B - preferred fix: compiler lowers math builtins to LLVM intrinsics
      https://github.com/openOODA-core/oodac/issues/3


--------------------------------------------------------------------------------
DEFECT A -- string primitives changed from codepoints to bytes
--------------------------------------------------------------------------------

SUMMARY

The oodar runtime was rewritten from C to openOODA (.oo) between the a53de08
commit and upstream master. The rewrite changed the meaning of two runtime
string primitives:

  primitive           C runtime (a53de08)              .oo runtime (master)
  ------------------  --------------------------------  -------------------------
  oo_chars_len(s)     number of UTF-8 codepoints       number of bytes (sl(s))
  oo_char_at(s, i)    the codepoint string at          the single byte at
                      codepoint index i                 byte index i

Evidence (both runtimes, same compiler 04adc274..., same std 72c26be1):

    s = "a<block>b"        (5 bytes, 3 codepoints)

    C runtime:    bytes_len=5  chars_len=3  char_at(s,1)="<block>"
    .oo runtime:  bytes_len=5  chars_len=5  char_at(s,1)="\xE2"

Source of the change:

  old: oodar/core/str/str_ops.c
       oo_chars_len walks the UTF-8 sequence and counts codepoints (with an
       ASCII fast path).

  new: oodar/core/oodar/src/host/str/str_ops.oo:101
         export fn oo_chars_len(s: String) -> Int { return sl(s); }
       and oodar/core/oodar/src/host/str/str_ops.oo:106
         export fn oo_char_at(s: String, i: Int) -> String {
             if i < 0 || i >= sl(s) { return rt_pack_oostr(0, 0); }
             return oo_str_ascii_intern(rt_load_u8(sp(s), i));
         }

  oo_str_slice and oo_str_index_of (via find_sub, which walks raw byte
  pointers) are byte-based as well.

WHY IT MATTERS

Rust's str::chars() counts codepoints, so the upstream semantics change breaks
every port that iterates a string by index and expects UTF-8 characters.
Concretely, in idlescreen:

  - the 7-row wordmark font atlas is a string of U+2588; a byte walk never
    matches the block glyph and flattens the whole font to dots;
  - a centred banner is measured with chars_len, so a string containing the
    four-pointed-star glyph is padded two columns short and the box no
    longer lines up;
  - a substring search over a multi-byte string stops matching.

Both the released hub asset (openOODA/install release hub, published 2026-11-08)
and a runtime built from upstream master behave the new way, so this is not a
stale-download problem.

SUGGESTED FIX

Restore codepoint semantics in the runtime, or make the change explicit and
versioned:

  - oo_chars_len should count codepoints (the C implementation is a drop-in
    reference), and
  - oo_char_at should return the codepoint string at a codepoint index.

If byte semantics are intended, then str_slice, chars_len and char_at need one
coherent definition and the semantic change has to be announced, because it
silently changes the output of every UTF-8 renderer built against the previous
runtime.


--------------------------------------------------------------------------------
DEFECT B -- transcendental math is no longer libm-compatible
--------------------------------------------------------------------------------

SUMMARY

The same rewrite replaced the C runtime's libm-backed math with a pure-.oo
approximation. The new pow/sqrt/sin/cos are accurate to ~1-2 ulp, but they are
NOT bit-compatible with glibc. Any consumer whose reference values come from
libm (Rust's f64::powf, f64::sqrt, f64::sin, ...) now disagrees in the last
bits.

SOURCE OF THE CHANGE

oodar/core/oodar/src/host/sys/math_ops.oo:

    pub fn math_sqrt(x: Float) -> Float {              // line 33
        ...
        let mut g: Float = bits_to_f64((bits >> 1) + 2303575421549936640);
        let mut i: Int = 0;
        while i < 8 { g = 0.5 * (g + x / g); i = i + 1; }   // 8 Newton steps
        return g;                                           // from a bit seed
    }

    pub fn math_pow(x: Float, y: Float) -> Float {      // line 120
        ...
        return math_exp(y * math_ln(x));                // exp/ln in plain f64
    }

    pub fn math_sin(x: Float) -> Float { ... }          // line 157
    pub fn math_cos(x: Float) -> Float { ... }          // line 175
    pub fn math_exp(x: Float) -> Float { ... }          // line 46
    pub fn math_ln(x: Float) -> Float { ... }           // line 79

  math_sin / math_cos are 2-term Cody-Waite plus a 10-term Taylor series.

The old C runtime was a thin, exact wrapper:

    double oo_ln(double x)   { return log(x); }
    double oo_exp(double x)  { return exp(x); }
    double oo_sqrt(double x) { return sqrt(x); }
    double oo_pow(double b, double e) { return pow(b, e); }

EVIDENCE

Bit patterns of the same expression under the C runtime, the .oo runtime and
glibc (via Rust f64::powf/sqrt):

  expression      glibc / Rust             C runtime  .oo runtime  delta ulp
  --------------  -----------------------  ----------  -----------  ----------
  pow(0.8, 2.0)   0x3fe47ae147ae147c       same       0x3fe47ae147ae147b   1
  pow(0.8, 4.0)   0x3fda36e2eb1c432e       same       0x3fda36e2eb1c432f   1
  pow(1.5, 3.0)   0x400b000000000000       same       0x400b000000000002   2
  pow(2.0, -6.0)  0x3f90000000000000       same       0x3f90000000000002   2
  sqrt(2.0)       0x3ff6a09e667f3bcd       same       0x3ff6a09e667f3bcc   1
  cos(pi * 0.6)   0xbfd3c6ef372fe94e       same       0xbfd3c6ef372fe94f   1

Measured across the 31 easing variants x 100 ratios used by the idlescreen
parity engine, the .oo runtime disagrees with glibc on 23 of the 31 variants
(up to 4096 ulp where the result is near zero). The old C runtime disagreed on
NONE.

WHY IT MATTERS

idlescreen ships a Rust reference implementation and a .oo port whose parity is
asserted with bit-exact frame hashes (51 scenes, qa/golden/). The goldens are
the Rust output; the Rust reference reproduces all 51 bit-exactly. Under the
.oo runtime the port's output diverges:

  scene      divergence under the .oo runtime
  ---------  --------------------------------------------------------
  sweep      220 frames; 11 entries differ (10 frames + the done digest)
  swarm      1030 frames; 3 entries differ (2 frames + the done digest)
  fireworks  the scene runs 18 frames longer (446 -> 464 frames) before it
             settles; 401 entries differ (382 frames + 18 extra frames + the
             done digest)

The fireworks case is not a rounding artefact: path completion depends on an
integer truncation of a float, so a 1-ulp difference changes the number of
frames the scene stays alive -- a visible difference in the shipped animation.
It also drifts the reveal timing enough that 382 of the 446 shared frames
render with a different content hash.

IMPORTANT: A "MORE ACCURATE" REIMPLEMENTATION WOULD *NOT* FIX THIS

glibc's pow is NOT correctly rounded. Over 100000 sample points:

    pow(x, 2.0)  != x * x            : 78 cases
    pow(x, 0.5)  != sqrt(x)          : 75 cases
    pow(x, 3.0)  != x * x * x        : 26108 cases

So a correctly-rounded pow/sqrt implemented in .oo would still disagree with
the goldens in ~0.08 % of cases (exponent 2) and far more for other
exponents. ONLY a libm-backed implementation reproduces the reference
bit-for-bit. Any fix must restore glibc, not improve on it.

SUGGESTED FIX (PREFERRED)

Make the COMPILER lower the math builtins to LLVM intrinsics so clang emits
libm calls, instead of routing them to the runtime's oo_* shims:

    pow  ->  llvm.pow.f64      sin  ->  llvm.sin.f64
    cos  ->  llvm.cos.f64      sqrt ->  llvm.sqrt.f64
    exp  ->  llvm.exp.f64      ln   ->  llvm.log.f64

clang++ already links -lm on every build line
(oodac/cli/build/cli_build.oo:65, :122, :127), so no new dependency is needed.
The runtime's pure-.oo math_ops can stay for runtime-internal use -- it would
itself be compiled against libm and inherit the same exactness.

This restores bit-exact parity for every libm-based consumer and keeps the
runtime free of a C dependency for its own internals.

The compiler-side change is filed separately in openOODA-core/oodac:
  https://github.com/openOODA-core/oodac/issues/3

SUGGESTED FIX (FALLBACK)

If the runtime must stay pure-.oo, the only remaining option is to reimplement
glibc's exact algorithms (its exp/log tables and branch logic) so the last bit
matches. That is not practical to maintain, so we would treat it as "no fix
available" and adapt on the consumer side instead.

--------------------------------------------------------------------------------
CONSUMER-SIDE MITIGATION (idlescreen)
--------------------------------------------------------------------------------

While the upstream fix is pending, idlescreen keeps its Rust goldens untouched
and quarantines the three affected scenes behind an explicit, documented list
(qa/parity_quarantine.txt). Each entry records the measured ceiling of the
divergence it defers -- how many entries may differ from the golden and how
many frames the scene may render -- so the gate fails when the actual
divergence exceeds it. The gate still fails on any OTHER divergence, and the
quarantined scenes are reported rather than silently dropped. The product
difference is bounded and documented: the reveal timing drifts in sweep and
swarm, and fireworks renders 18 frames longer and settles later than the
golden.

The full report is also filed upstream as the three issues listed at the top of
this file.
